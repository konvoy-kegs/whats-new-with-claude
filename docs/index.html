CLI · v2.1.259 on latest and next
All sources aligned on v2.1.259. npm's newest publish, the latest dist-tag, the next dist-tag, the changelog top entry and the GitHub release tag all agree — no divergence to reason about today. It published this morning at 07:21 local and was tagged on GitHub at 08:33, so claude update already installs it. 37 changelog entries — the third substantial release in three days, after v2.1.257 (104 entries) and the two-line v2.1.258 hotfix.
One change needs attention before you upgrade: allowedMcpServers no longer filters managed MCP servers. “Changed allowedMcpServers to govern only servers users add: a literal managed-mcp.json server your allowlist used to filter out now loads on upgrade; use deniedMcpServers to keep it off.” If we are relying on an allowedMcpServers allowlist to suppress a managed MCP server, that suppression stops working the moment anyone updates. The replacement control is deniedMcpServers, and it has to be set before the rollout, not after.
Two items that matter for our infrastructure: org-wide managed MCP servers, and a headless permission mode that denies instead of hanging. The new managedMcpServers managed setting lets us push HTTP/SSE MCP servers to every user from one place (same entry shape as .mcp.json; command-launched entries are skipped). --permission-prompts none makes unattended hosts deny anything that would prompt while the active permission mode keeps deciding — the correct default for CI runners, which previously either hung or needed a blunt bypass flag.

v2.1.259 — managed MCP servers, headless permission denial, and four more enforcement gaps closed today's headline

Added managedMcpServers: organizations can provide HTTP/SSE MCP servers to every user. Same entry shape as .mcp.json; entries that name a command to run are skipped. This is the piece that was missing for centrally distributing our internal MCP servers — until now every engineer configured them individually, or we shipped them inside a plugin. Note the deliberate restriction to HTTP/SSE: a managed setting cannot make every machine execute a local binary, which is the right call.
Added --permission-prompts none for unattended headless hosts. Anything that would prompt is denied automatically, while the active permission mode — including auto mode — keeps deciding everything else. This is the flag CI has needed. The previous options were a session that blocks forever waiting for a human, or --permission-mode bypassPermissions, which throws away the permission model entirely. This keeps the model and treats “needs a human” as a denial.
Fixed concurrent sessions silently reverting each other's ~/.claude.json changes. Workspace trust no longer resets and MCP/project state is no longer lost when running many sessions at once. Anyone running several sessions in parallel — agent teams, background sessions, a tmux grid — has been losing configuration writes without any error. If workspace trust prompts have been reappearing for no apparent reason, or an MCP server keeps vanishing from a project, this was why.
Fourth consecutive release with a Bash deny-rule matcher correction. Read() deny rules were not covering files passed as option values (--ignore-revs-file=.env, -f.env, @file), git diff/git grep file operands, or cd DIR && cat FILE compounds. grep -r/cp -r over a directory holding a denied file now asks. The pattern here is unambiguous: a deny rule written as a filename does not reliably deny every way a shell can name that file. Treat Bash deny rules as defence in depth behind sandboxing, not as the boundary itself.
Fixed managed settings silently going unenforced when they cannot be parsed — Claude Code now refuses to start and names the source. Applies to the managed-settings file, a drop-in, the MDM plist, or the HKLM value. A malformed managed-settings file used to mean no policy at all, reported as nothing. Fail-closed is correct, but plan for it: a bad deploy of managed settings now stops the CLI launching org-wide rather than quietly degrading. Validate before rollout.
Fixed forceRemoteSettingsRefresh being ignored at startup when an MDM or managed-settings policy helper had already run. Another case where an administrator control appeared configured and was not in force. Third such fix in three releases.
Fixed the prompt cache being invalidated when the OAuth token refreshed in sessions with telemetry disabled. A silent cost item: every token refresh in a telemetry-disabled session threw away the cache and re-sent the conversation uncached. Paired with today's fix for blocking Stop hooks causing the next turn to lose reasoning and miss the cache.
Fixed Stop not actually stopping background agents and workflows in remote-control sessions. Killed tasks now stay visible and re-stoppable until their processes exit. Also fixed: resuming a workflow run while its previous stopped run was still exiting could run duplicate copies of its agents. If a stopped workflow has ever appeared to keep working, that was real.
GitLab support continues to fill in. glab mr create/merge/close/reopen/note/update is now recognised, so merge requests show as MR !N in the collapsed tool summary and refresh the footer MR badge. /install-github-app now explains it is GitHub-only and points to the GitLab CI/CD docs when run inside a GitLab repository.
Also worth knowing: --json on claude plugin validate for a machine-readable validation report (useful in a marketplace CI check); MCP servers that disconnect while their tools are being listed at startup now report the error instead of showing as connected with no tools; worktree-isolated sessions no longer refuse common Bash loops, xargs pipelines and launcher-wrapped commands; --resume no longer fails on a saved session containing an attachment entry with no payload; and marketplace repo URLs with a trailing slash or dangling ?/# no longer produce an unusable clone URL.

This week's actionable items

  • check first Before rolling out v2.1.259, audit every allowedMcpServers allowlist for managed MCP servers it was suppressing. The setting now governs only user-added servers, so a managed-mcp.json server the allowlist used to filter out loads on upgrade. Move those to deniedMcpServers before anyone updates — this is the one item on this list that gets worse, not better, when you patch.
  • validate Validate our managed-settings payload before the next deploy. v2.1.259 makes an unparseable managed-settings file, drop-in, MDM plist or HKLM value refuse to start the CLI and name the source. Correct behaviour — silent non-enforcement was worse — but a malformed deploy is now an org-wide outage rather than a quiet policy gap. Add a parse check to whatever ships it.
  • enable Set --permission-prompts none on unattended runners. New in v2.1.259. Anything that would prompt is denied while the active permission mode keeps deciding. This replaces bypassPermissions as the correct headless posture — if any of our CI jobs still pass bypassPermissions to get past prompts, that is now an unnecessary hole.
  • re-read Your Bash Read() and Edit() deny rules. Fourth release running. v2.1.259 fixed deny rules missing files given as option values (--ignore-revs-file=.env, -f.env, @file), git diff/git grep operands, and cd DIR && cat FILE compounds. The recurring lesson: a filename-based deny rule is not a boundary. Sandboxing and blockReadsOutsideWorkingDirectories are.
  • enable Turn on permissions.blockReadsOutsideWorkingDirectories in managed settings (v2.1.257) if you have not yet. Reads outside the working directory are how a session reaches ~/.aws/credentials, ~/.ssh, or another repo's .env. Given today's deny-rule fixes, this is the control that actually holds.
  • verify Confirm the Containment Escape rule behaves on our EC2 and EKS runners (v2.1.257). Cloud metadata-credential fetches, egress evasion and cross-tenant reach are no longer auto-approved in auto mode unless the environment marks them expected. Any legitimate workflow that reads instance metadata will now stop and ask — find those before they surface as a stuck pipeline.
  • re-check Managed policy enforcement generally — three fixes in three releases. Today: forceRemoteSettingsRefresh ignored at startup when a policy helper had already run. v2.1.257: --disallowedTools and session deny rules dropped after the first settings reload under allowManagedPermissionRulesOnly; /mcp reconnect connecting a server a managed list should block. Configuring a policy and verifying it applies are different activities.
  • audit Write access to any GitHub repo backing a private plugin marketplace — fifth consecutive week. v2.1.259 adds --json to claude plugin validate, which makes a CI gate on marketplace content straightforward to build. v2.1.257 fixed plugins reading outside their own directory through symlinked component paths.
  • rotate Bedrock, Vertex, Mantle, WIF and Foundry credentials where a custom Authorization header is configured (v2.1.257 fixed three paths that sent the wrong credential to the wrong host), and credentials from uncommitted *.tfvars, prod.env or stray .pem files in repos used with /ultrareview or a cloud session (v2.1.248).
  • unpin Move anything pinned to the stable dist-tag. stable is v2.1.236 from 20 Aug — seventeen releases and every fix on this list behind.

Patterns worth tracking

Fail-closed is now the consistent direction of travel, and it has an operational cost. This release refuses to start when managed settings cannot be parsed, refuses to launch on unparseable MDM values, denies rather than hangs on headless prompts, and reports MCP servers that fail mid-listing instead of showing them as connected-with-no-tools. Every one of these turns a silent degradation into a loud failure. That is the correct trade, but it moves the failure into our deploy pipeline: things that used to quietly not work will now stop the CLI. Validate managed settings and MCP config as build artifacts.
Bash permission matching has been corrected in four consecutive releases, which tells us where not to put our trust. Option values, git operands, cd && compounds and recursive grep/cp today; < file redirects, tac/egrep, [[ ]] zsh conditionals and compound-command ask rules over the preceding three. The shell has too many ways to name a file for a pattern matcher to enumerate. Deny rules are useful for catching mistakes; sandboxing, working-directory limits and least-privilege credentials are what stop an adversary.
Multi-session state was never safe and is only now being made so. Concurrent sessions silently reverting each other's ~/.claude.json — losing workspace trust and MCP/project state — is a data-integrity bug affecting exactly the parallel-agent workflows the product has been pushing. If we have been debugging “why did trust reset” or “why did that MCP server disappear”, stop; it was this.

Claude Desktop

macOS · Windows · Linux (beta)

What's new

New in v2.1.259 — a background GitHub connection check that ran on every launch for claude.ai users is now remembered across launches. Small but user-visible: every Desktop-hosted session start was making a GitHub probe it did not need. Startup should feel marginally quicker, and one less outbound call per launch matters if you are watching egress.
New in v2.1.259 — OpenTelemetry metrics and events from cloud sessions were missing user.email, organization.id and user.account_uuid. If we attribute Claude usage per-user from a central collector, cloud-session telemetry has been arriving unattributable. Anything built on those attributes has an under-counted gap for cloud sessions up to this release. Paired with v2.1.257's fix for server-managed OTEL settings being ignored on warm starts, including desktop-app Code sessions.
Carried forward — Remote Control sessions started from the Claude app now honour the model you selected (v2.1.257). They were running on the machine's default instead, with no notice. If you picked Opus in the app and the machine defaulted to Sonnet, you got Sonnet. Assume recent Desktop-launched Remote Control sessions may not have been on the model you chose.
Carried forward — Remote Control stalls on a degraded connection are fixed (v2.1.252), and the 30-day session deletion fix (v2.1.248) stopped the CLI's transcript cleanup reaping desktop-written sessions the app still considered live. Anything already reaped before that release is gone; upgrading does not recover it.
Standing context — memory, the Customize panel, and Cowork GA. Everything Claude remembers is listed under Topics in Settings > Memory and can be edited or deleted. Memory is on by default for Free, Pro and Max, and off by default for Team and Enterprise — on our plan nothing is retained unless somebody turned it on. Also live: Cowork generally available on macOS and Windows; a Customize section grouping skills, plugins and connectors; the monthly recap at Settings > Reflect; break reminders and quiet hours at Settings > Time and focus.

Claude Cowork

GA · macOS & Windows

What's new

New in v2.1.259 — remote and scheduled sessions did nothing after a connector-tool permission prompt was approved while the session was paused. This digest is itself a scheduled Cowork task that calls connector tools, so this is precisely our failure shape. Second consecutive release fixing a way a scheduled session can appear to run and accomplish nothing: v2.1.258 fixed remote and scheduled sessions failing outright with “user messages must have non-empty content” after a re-sent permission approval could not be applied, and v2.1.257 fixed /schedule routines saved without a message role running with nothing to do. If a scheduled task has silently produced no output on any recent day, one of these three is the likely cause — and all three are fixed as of today.
New in v2.1.259 — Artifact publishing failed once with an “unexpected parameter note” error in conversations continued from an older version. A one-off failure on the first publish after resuming an older conversation. Relevant to us: this digest publishes to a Cowork artifact every run.
New in v2.1.259 — nested background subagent results are now saved in the parent subagent's transcript, so resumed subagents keep them and shared transcripts show the delivery. Also: Stop now actually stops background agents and workflows in remote-control sessions, and resuming a workflow run while its previous stopped run was still exiting no longer runs duplicate copies of its agents. For anyone orchestrating multi-agent Cowork work, duplicate-run and lost-result bugs were both real until today.
Carried forward — reading an artifact that is not yours always asks first, even in auto mode (v2.1.257). A deliberate carve-out from auto mode for cross-user data: auto mode no longer implies consent to open somebody else's artifact. Expect an extra prompt in shared workspaces; that is intended, not a regression.
Standing context — plugins, skills and scheduled tasks. Plugins bundle skills, connectors and sub-agents into one installable package, usable in chat on the web, the Chat tab in Desktop, and Cowork. Hooks and sub-agents run only in Cowork, so they appear greyed out in chat. In Cowork, Customize in the upper right opens a task that walks through tailoring an installed plugin to how you work. Recurring and on-demand scheduled tasks are available; Cowork sessions can run remotely in the cloud (beta) so scheduled tasks fire with no device online. Enterprise plans can turn on skill and plugin security scanning — worth enabling given five consecutive weeks of marketplace and plugin path fixes in the CLI, and now that claude plugin validate --json makes a CI gate easy.
